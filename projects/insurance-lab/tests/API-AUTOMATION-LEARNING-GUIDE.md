# API 自动化测试从零实战学习指南

> **学习方式：从零独立实现，现有代码只作为参考答案。**  
> 本指南面向 `projects/insurance-lab`，目标是逐步掌握 Python + Requests + pytest API 自动化测试，而不是直接复制一套现成框架。

## 1. 学习目标与约束

完成本路线后，应能够独立完成以下工作：

1. 阅读 Swagger / OpenAPI 文档，理解接口契约、请求参数、响应结构和状态码。
2. 根据需求、接口文档和业务流程设计可执行、可追踪的测试用例。
3. 使用 Python Requests 编写 HTTP API 测试，并正确处理响应、超时和异常。
4. 使用 pytest 管理测试发现、断言、参数化、Fixture 和测试生命周期。
5. 根据实际重复点逐步引入测试数据工厂、HTTP Client 和业务 API 层。
6. 验证接口响应、业务状态、跨接口流程以及失败请求的副作用。
7. 进一步开展数据库集成、事务、并发、幂等性和 CI 自动化测试。

### 1.1 从零练习原则

- 当前仓库已有的自动化代码并非本次学习者独立编写，**不能把“能运行现有代码”当作已经掌握**。
- `tests/api/` 下已有的测试脚本、用例文档和目录，只作为需求资料、对照样例和最终参考答案。
- 自己的练习代码放在独立目录 `tests/api_practice/`，不覆盖、不重命名、不直接改造现有 `tests/api/`。
- 初期不提前搭建完整框架。先直接使用 Requests 写出可理解、可验证的测试，再根据重复问题逐步抽象。
- 每个阶段都要经历：理解原理 → 阅读接口/需求 → 独立实现 → 执行验证 → 代码审查 → 总结复盘。
- 不为了目录整齐而过度封装；每个模块都必须有清晰职责和实际使用场景。
- 写入型测试必须使用专用测试环境和本次测试创建的数据，不得对生产库或含真实个人数据的数据库执行。

## 2. 练习项目与接口范围

练习项目：`projects/insurance-lab`。

当前测试资料列出的 API 基线如下。开始每个阶段前，仍需重新核对 Swagger/OpenAPI 和当前后端实现；如果需求、Swagger、代码和数据库约束不一致，应记录差异并确认预期，不能默认当前代码行为就是正确需求。

| 业务模块 | 方法 | 路径 | 主要练习内容 |
|---|---|---|---|
| 健康检查 | GET | `/health` | 最简单的 HTTP 请求、状态码和响应校验 |
| 申请列表 | GET | `/api/applications` | 列表响应、数据结构和查询行为 |
| 创建申请 | POST | `/api/applications` | JSON 请求体、字段校验、边界值和失败副作用 |
| 核保 | POST | `/api/applications/{id}/underwrite` | 状态转换、前置条件和非法状态 |
| 支付 | POST | `/api/applications/{id}/pay` | 幂等性、支付结果和资金/保单一致性 |
| 保单列表 | GET | `/api/policies` | 列表查询和数据关联 |
| 保单详情 | GET | `/api/policies/{id}` | 资源定位、存在/不存在和响应契约 |

核心业务流程：

`创建申请 → 核保 → 支付 → 查询保单`

练习中要区分三种测试边界：

| 测试类型 | 测试对象 | 典型方式 |
|---|---|---|
| Unit（单元测试） | 独立业务规则、校验器、状态转换等，不依赖 HTTP 和真实数据库 | 通常由后端 C# 单元测试执行 |
| Integration（集成测试） | API、数据访问层、EF Core、PostgreSQL、事务和约束之间的协作 | pytest + HTTP + 专用测试数据库，或后端集成测试 |
| Functional API（接口功能测试） | 从调用方视角验证 HTTP 契约、业务结果和副作用 | pytest + Requests 调用运行中的 API |
| Workflow（业务流程测试） | 多个接口组合后的业务不变量 | pytest + Requests 执行完整业务链 |

不要把所有通过 HTTP 调用服务的测试都称为单元测试。

## 3. 分阶段学习路线

## 阶段 0：项目与接口认知

**目标：** 在不写自动化代码的情况下，能够说明被测系统是什么、如何运行、接口如何协作，以及测试数据存在哪里。

### 学习与实施任务

1. 阅读 `projects/insurance-lab` 的项目说明，确认前端、后端、测试目录和启动方式。
2. 确认 API Base URL、端口、运行配置和环境变量来源。
3. 启动后端，打开 Swagger / OpenAPI，逐个检查上述接口。
4. 对每个接口记录：HTTP 方法、路径、Path 参数、Query 参数、Headers、请求体、响应体、状态码和错误响应。
5. 使用 Swagger 或 Postman 手动调用接口，至少完成一次成功流程和若干失败请求。
6. 理解申请状态、核保结果、支付记录和保单之间的关系。
7. 确认数据库连接目标，明确哪些数据库允许测试写入，如何重置或清理测试数据。
8. 对照现有 `tests/api/functional/` 文档，识别需求、接口文档和实现之间的差异。

### 建议产出

- `api_practice/notes/project-environment.md`：运行方式、Base URL、环境配置和安全注意事项。
- `api_practice/notes/api-inventory.md`：接口清单和请求/响应契约。
- `api_practice/notes/business-workflow.md`：业务状态和跨接口流程图。
- `api_practice/notes/open-questions.md`：需求、Swagger、代码或数据库约束之间待确认的问题。

### 验收标准

- 不看实现代码，也能解释每个接口的输入、输出和业务职责。
- 能手动调用健康检查、创建申请、核保、支付和保单查询接口。
- 能描述成功流程及关键失败场景。
- 知道当前 API 使用哪个数据库，并能证明它是专用测试环境。
- 能指出需求不明确或文档不一致之处，而不是自行猜测。

## 阶段 1：Requests 与 pytest 基础测试

**目标：** 不依赖自定义 HTTP Client 或业务 API 封装，独立写出第一个可执行的 API 测试。

### 学习知识点

- Python 模块、函数、导入和异常基础。
- HTTP 方法、URL、Headers、Query Parameters 和 JSON Body。
- Requests 的 `get()`、`post()`、`params`、`json`、`headers`、`timeout`。
- Response 的 `status_code`、`headers`、`text`、`json()`。
- HTTP 状态码与业务状态字段的区别。
- pytest 测试发现规则、测试函数命名和 `assert`。
- 请求超时、连接失败和 JSON 解析异常的基本识别。

### 实施任务

1. 先创建最简单的健康检查测试文件。
2. 直接使用 Requests 发送 GET 请求。
3. 断言状态码、Content-Type 和响应 JSON 的关键字段。
4. 为请求设置合理的 timeout，避免测试无限等待。
5. 编写创建申请的正向测试，明确请求体和响应预期。
6. 编写字段缺失、非法值和边界值等负向测试。
7. 每个测试都独立表达自己的前置条件、动作和预期，不依赖其他测试先运行。
8. 运行单个测试、单个文件和整个练习目录，观察 pytest 的收集和报告结果。

### 建议目录

```text
tests/api_practice/
├── basics/
│   ├── test_health.py
│   └── test_applications_basic.py
└── README.md
```

### 验收标准

- 能从零编写并运行健康检查和创建申请测试。
- 能解释 Requests 请求参数和 Response 常用属性。
- 能区分 HTTP 层失败、业务校验失败和测试断言失败。
- 测试失败时能定位是连接、超时、响应解析还是预期不符。
- 不需要复制现有测试脚本即可完成基础测试。

## 阶段 2：测试数据管理

**目标：** 把测试数据的构造与 HTTP 请求行为分离，降低重复数据和测试间相互影响。

### 学习知识点

- 测试数据准备（Arrange）与测试动作（Act）的职责边界。
- 合法数据、非法数据、边界数据和组合数据。
- 唯一标识、UUID、时间戳和幂等键的使用场景。
- 数据清理策略、测试隔离和可重复执行。
- Python 字典复制、默认参数和可变对象风险。
- 金额类字段的精度问题；金额比较应按接口契约选择 Decimal 或规范化后的十进制字符串，避免直接依赖二进制浮点数相等。

### 实施任务

1. 将创建申请所需的默认合法请求体整理为数据工厂。
2. 支持通过参数覆盖年龄、产品编码、保费等字段。
3. 为必填缺失、空字符串、超长文本、非法类型和边界值准备专门数据。
4. 为每次写入型测试生成唯一申请数据，避免重复运行时冲突。
5. 单独实现幂等键生成逻辑，并理解同一键重试与不同键请求的差异。
6. 确保工厂只生成数据，不发 HTTP 请求、不做业务断言、不直接操作数据库。
7. 设计测试数据的清理或隔离策略，并验证重复执行不会污染其他测试。

### 建议目录

```text
tests/api_practice/
└── data/
    ├── __init__.py
    └── application_factory.py
```

### 方法职责提示

- `build_application_payload(...)`：返回申请请求数据。
- `build_invalid_application_payload(...)`：构造非法输入，或通过参数化组合实现。
- `build_unique_idempotency_key(...)`：生成本次测试使用的幂等键。

### 验收标准

- 测试方法不再散落大量重复请求体。
- 修改一个测试数据字段不会意外改变其他测试共用的数据。
- 每次写入型测试的数据可区分、可追踪。
- 数据工厂不包含 Requests 调用和测试断言。

## 阶段 3：HTTP 通信层封装

**目标：** 在已经理解 Requests 的基础上，封装重复的 HTTP 通信配置，而不是隐藏测试行为。

### 学习知识点

- `requests.Session()` 与模块级 `requests.get/post()` 的区别。
- Session 的连接复用、公共 Headers 和 Cookie 管理。
- Base URL 与相对路径拼接。
- 统一 timeout、默认 Headers 和请求级参数覆盖。
- HTTP 请求异常与 HTTP 错误状态码的区别。
- Session 生命周期与关闭时机。
- 日志中敏感信息的脱敏。

### 实施任务

1. 创建独立的 HTTP Client 模块。
2. 在初始化时接收 Base URL、timeout 和可选公共 Headers。
3. 创建并维护一个 `requests.Session`。
4. 实现统一的 `request(method, path, **kwargs)`。
5. 根据实际使用需求提供 GET、POST、PUT、PATCH、DELETE 快捷方法。
6. 统一拼接 URL，支持请求级参数覆盖默认配置。
7. 明确网络异常如何向测试层传递；不要把异常静默吞掉。
8. 保留原始 Response，不在底层自动断言业务结果。
9. 不默认对写操作自动重试；尤其支付等请求必须先理解幂等契约和重试风险。
10. 提供显式关闭 Session 的能力。

### 建议目录

```text
tests/api_practice/
└── core/
    ├── __init__.py
    └── http_client.py
```

### 方法职责提示

- `__init__()`：保存基础配置并初始化 Session。
- `request()`：统一发送请求。
- `get()/post()/put()/patch()/delete()`：薄封装常用 HTTP 方法。
- `close()`：释放 Session 资源。

### 验收标准

- 通过封装类能够完成健康检查和创建申请请求。
- 所有请求都有明确的 timeout。
- 负向测试能够正常取得并断言 400、404、409 等 Response。
- 网络连接异常不会被误报成业务断言失败。
- HTTP Client 不包含保险业务规则和 pytest 断言。

## 阶段 4：pytest Fixture 与环境配置

**目标：** 使用 pytest 管理 HTTP Client 的创建、注入和释放，并支持不同测试环境配置。

### 学习知识点

- Fixture 的定义、依赖关系和参数注入。
- `yield` 前后的初始化与清理。
- `function`、`class`、`module`、`session` scope 的区别。
- `conftest.py` 的发现规则和作用范围。
- 环境变量、默认值和配置校验。
- 测试环境与生产环境隔离。
- Fixture 组合、间接参数化和自动使用 Fixture 的场景。

### 实施任务

1. 创建配置模块，集中读取 API Base URL 和 timeout。
2. 明确配置优先级，例如环境变量覆盖安全的本地默认值。
3. 对缺失或非法配置给出清晰错误，不要静默连接错误地址。
4. 创建 function scope 的 HTTP Client Fixture。
5. 使用 `yield` 返回 Client，并在测试结束时关闭 Session。
6. 练习让同一测试中的多个业务 API 对象共享同一个 HTTP Client。
7. 验证一个测试失败时清理逻辑仍然执行。
8. 验证测试之间不会共享不应共享的状态。

### 建议目录

```text
tests/api_practice/
├── config/
│   ├── __init__.py
│   └── settings.py
└── conftest.py
```

### 验收标准

- 测试方法不再负责创建和关闭 Session。
- 能解释 Fixture 的依赖注入和作用域。
- 测试结束后资源能正确释放。
- 可以通过环境变量切换 API 地址和 timeout。
- 不会因为配置缺失而意外向生产环境发送写请求。

## 阶段 5：业务 API 层封装

**目标：** 把保险业务接口路径和请求组织集中管理，让测试代码聚焦业务场景和预期结果。

### 学习知识点

- HTTP 通信层与业务 API 层的职责边界。
- 组合（Composition）和依赖注入。
- API 对象如何共享底层 HTTP Client。
- 业务资源路径、Path 参数和请求体的组织。
- API 方法返回 Response，而不是擅自决定测试是否通过。

### 实施任务

1. 创建 Application API 类，封装申请创建和申请查询。
2. 创建 Underwriting API 类，封装核保操作。
3. 创建 Payment API 类，封装支付操作和幂等键传递。
4. 创建 Policy API 类，封装保单列表和详情查询。
5. 每个类通过构造函数接收共享的 HTTP Client。
6. 方法负责路径、参数和请求体组织，并返回原始 Response。
7. 不在业务 API 类中写 pytest assert。
8. 不把完整业务工作流塞进单个 API 方法；工作流应由测试场景编排。

### 建议目录

```text
tests/api_practice/
└── clients/
    ├── __init__.py
    ├── application_api.py
    ├── underwriting_api.py
    ├── payment_api.py
    └── policy_api.py
```

### 验收标准

- 测试方法不需要重复拼接业务接口路径。
- 每个 API 类职责单一，方法名与业务操作对应。
- 不同业务 API 对象能够共享同一个 HTTP Client。
- API 类不隐藏状态码、业务断言或测试步骤。

## 阶段 6：完整 API 功能测试体系

**目标：** 将接口契约测试扩展为覆盖正向、负向、边界、状态、副作用和跨接口工作流的系统测试集。

### 学习知识点

- 等价类划分、边界值分析和决策表。
- pytest 参数化、Fixture 组合和测试标记。
- 响应字段、数据类型、必填字段和 JSON Schema。
- HTTP 状态码、业务状态和持久化结果的多层断言。
- 失败请求的副作用验证。
- 测试报告、日志、失败证据和缺陷追踪。
- 独立测试、可重复执行和测试顺序无关。

### 实施任务

1. 根据每个接口的详细用例文档逐项实现测试，不要只按页面或模块写一两个 happy path。
2. 为每个字段覆盖正常值、边界值、缺失值、null、空字符串、空白字符串、非法类型和超长值（以契约为准）。
3. 验证成功响应的状态码、响应结构、关键字段和业务状态。
4. 验证失败响应的错误结构和明确的状态码。
5. 对失败写请求检查数据副作用：申请状态、支付记录和保单是否保持不变。
6. 编写完整工作流测试：创建申请 → 核保 → 支付 → 查询保单。
7. 验证重复支付、幂等键复用和跨申请幂等键冲突等业务行为。
8. 将通用结构校验与业务断言区分开；避免把所有断言都抽象成难以理解的工具方法。
9. 记录测试结果和缺陷编号，生成可供审查的执行报告。

### 建议目录

```text
tests/api_practice/
├── assertions/
│   └── response_assertions.py
├── schemas/
├── functional/
│   ├── test_health.py
│   ├── test_applications.py
│   ├── test_underwriting.py
│   ├── test_payment.py
│   ├── test_policies.py
│   └── test_insurance_workflows.py
└── reports/
```

### 验收标准

- 每个已纳入范围的接口都有独立、可追踪的测试覆盖。
- 正向、负向、边界和状态转换用例均有明确预期。
- 写操作失败时，不只断言状态码，还验证关键副作用。
- 跨接口流程不依赖其他测试创建的数据。
- 测试可以重复运行，失败信息足以定位问题。
- 测试分类与真实测试边界一致。

## 阶段 7：高级 QA 能力与 CI

**目标：** 从接口功能自动化进一步提升到数据一致性、并发安全和持续集成验证。

### 学习知识点与实施任务

| 主题 | 练习内容 | 关键关注点 |
|---|---|---|
| Unit Test | 业务校验、金额规则、状态转换和幂等规则 | 独立逻辑、快速反馈，不依赖 HTTP/真实 DB |
| Integration Test | API、数据访问层和 PostgreSQL 协作 | 专用测试库、隔离、事务与清理 |
| 事务 | 成功提交、异常回滚 | 失败后数据是否部分写入 |
| 数据约束 | 唯一键、外键、非空和长度限制 | 数据库约束与 API 校验的一致性 |
| 幂等性 | 相同 key 重试、不同 key、跨申请复用 | 是否产生重复支付或重复保单 |
| 并发 | 同一申请并发支付、不同申请并发支付 | 竞态条件、锁、唯一约束和最终状态 |
| 故障场景 | 超时、连接中断、服务异常 | 重试策略、未知提交结果和恢复行为 |
| CI | GitHub Actions 执行测试 | 环境配置、测试数据库、报告和失败产物 |

### 安全与可靠性要求

- 并发、事务回滚和故障注入必须使用专用、可重置的测试环境。
- 不要在共享开发库或生产库执行破坏性测试。
- 不要仅通过客户端超时就断言服务端没有完成写入；超时可能发生在服务端提交之后。
- 支付类重试必须验证幂等语义，不能简单地对所有 POST 自动重试。
- 数据库校验应优先使用本次测试创建的业务 ID，不依赖固定 ID 或全表数量。
- CI 中不得提交真实密码、连接字符串凭据或个人数据。

### 验收标准

- 能区分单元、集成、接口功能和端到端业务流程测试。
- 能验证支付幂等、事务原子性和并发下的数据一致性。
- 能解释超时后请求结果不确定的风险。
- 能在 CI 中安全启动测试依赖并执行测试。
- 测试失败时能从报告和日志定位具体用例与缺陷。

说明：

## 5. 每个阶段的固定学习与代码审查流程

每个小任务均按以下顺序进行：

1. **原理说明**：先解释要解决的问题、底层机制和适用边界。
2. **需求拆解**：明确接口契约、前置条件、测试数据、执行动作和预期结果。
3. **实现提示**：明确需要创建的文件、类、方法、参数、返回值和职责；初次练习不直接给出完整答案。
4. **独立编码**：学习者自行实现，并能解释每一段代码。
5. **执行验证**：运行指定测试，观察真实请求、响应和失败信息。
6. **代码审查**：检查职责划分、可读性、异常处理、测试隔离、断言质量和安全性。
7. **修正与复测**：修复问题并重新运行相关测试和回归测试。
8. **对照复盘**：最后再对照仓库已有实现，讨论不同设计的优缺点。
9. **阶段验收**：只有达到该阶段验收标准，才进入下一阶段。

每次练习建议只推进一个清晰的小目标，例如“完成健康检查请求与响应断言”，不要一次性生成整个框架。

## 6. 推荐的第一批实际任务

正式写框架前，按以下顺序开始：

1. 确认后端启动命令、API Base URL 和专用测试数据库。
2. 阅读 Swagger，完成接口清单和业务流程笔记。
3. 手动调用 `GET /health` 和 `POST /api/applications`。
4. 独立设计健康检查接口的正向与异常测试预期。
5. 在 `api_practice/basics/test_health.py` 中直接使用 Requests 完成第一个 pytest 测试。
6. 运行并解释测试结果，再由代码审查确认是否进入创建申请测试。

**第一阶段不创建 HttpClient、不创建业务 API 类、不提前设计完整 Fixture 体系。** 这些内容在你遇到真实重复问题后再逐步引入。
