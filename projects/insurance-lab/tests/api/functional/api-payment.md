# POST /api/applications/{id}/pay — API 测试用例

## 接口契约基线

只有 Approved 申请允许首次支付。成功支付应将申请改为 Paid，创建一条 Succeeded 支付记录和一张 Active 保单。相同幂等键重试应返回同一支付/保单结果；已被其他申请使用的键应返回 409。当前代码对空幂等键生成默认键 application-{id}-payment。

## 用例

### FT-PAY-001 — Approved 申请首次支付成功

- 优先级：P0
- 类型：功能 / 主流程
- 前置条件：创建申请并核保通过；记录 applicationId 和 premium。
- 数据：唯一 idempotencyKey。
- 步骤：
  1. POST /api/applications/{id}/pay。
  2. 检查响应体。
  3. GET /api/applications，检查申请状态。
  4. GET /api/policies，按 applicationId 检查保单。
- 预期结果：
  1. HTTP 200。
  2. applicationId 与请求 ID 一致。
  3. paymentId 为正整数，paymentStatus=Succeeded。
  4. policyNumber 非空且符合当前格式 LAB- 加 8 位补零 ID；policyStatus=Active。
  5. duplicate=false。
  6. 申请状态变为 Paid。
  7. 恰好存在一张关联保单，保费和申请一致。
- 状态：现状可验证。

### FT-PAY-002 — Pending 申请禁止支付

- 优先级：P0
- 类型：负向 / 状态机
- 前置条件：创建申请但不核保。
- 数据：唯一幂等键。
- 步骤：调用支付接口，再查询申请和保单列表。
- 预期结果：HTTP 409；申请仍为 Pending；不创建支付记录或保单。
- 状态：现状可验证。

### FT-PAY-003 — Rejected 申请禁止支付

- 优先级：P0
- 类型：负向 / 状态机
- 前置条件：申请核保拒绝。
- 数据：唯一幂等键。
- 步骤：调用支付接口，再查询申请和保单。
- 预期结果：HTTP 409；申请仍为 Rejected；无支付记录和保单。
- 状态：现状可验证。

### FT-PAY-004 — 不存在的申请 ID 支付

- 优先级：P1
- 类型：负向 / 资源不存在
- 前置条件：ID 在测试库不存在。
- 数据：不存在的正整数 ID。
- 步骤：调用支付接口。
- 预期结果：HTTP 404；不创建支付或保单；错误体不泄露内部信息。
- 状态：现状可验证。

### FT-PAY-005 — 已支付申请使用同一幂等键重试

- 优先级：P0
- 类型：幂等 / 回归
- 前置条件：Approved 申请首次支付成功。
- 数据：第一次支付所用的同一个 idempotencyKey。
- 步骤：
  1. 保存第一次响应的 paymentId 和 policyNumber。
  2. 使用相同 applicationId 和相同键再次请求支付。
  3. 查询该申请关联的保单。
- 预期结果：第二次 HTTP 200；duplicate=true；paymentId、policyNumber 与第一次相同；仅一笔支付和一张保单；申请仍为 Paid。
- 状态：现状可验证。

### FT-PAY-006 — 同一幂等键被另一申请复用

- 优先级：P0
- 类型：负向 / 幂等键隔离
- 前置条件：申请 A 已成功支付并使用键 K；申请 B 已核保通过。
- 数据：B 使用申请 A 的键 K。
- 步骤：
  1. 记录 A 的支付/保单结果。
  2. 使用 B 的 ID 和 K 请求支付。
  3. 查询 B 的申请状态和关联保单。
- 预期结果：B 返回 HTTP 409；响应不得返回 A 的 paymentId、policyNumber 或其他结果；B 仍为 Approved；B 不产生支付/保单；A 的数据不变。
- 状态：现状可验证。

### FT-PAY-007 — 同一申请使用不同幂等键重复支付

- 优先级：P0
- 类型：幂等 / 业务唯一性
- 前置条件：申请首次支付成功。
- 数据：第一次使用 K1，第二次使用不同的 K2。
- 步骤：使用 K2 再次调用支付，随后查询申请、支付和保单数据。
- 预期结果：不得创建第二张保单或第二笔成功支付；响应应按已批准的业务契约明确处理。当前实现预期因申请状态已 Paid 而返回 409，且不产生副作用。
- 状态：当前实现可验证；响应契约应确认。

### FT-PAY-008 — 幂等键缺失

- 优先级：P1
- 类型：边界 / 幂等
- 前置条件：一条 Approved 申请。
- 数据：请求体省略 idempotencyKey。
- 步骤：首次支付后，用同样不带键的请求再次支付。
- 预期结果：当前实现会生成 application-{id}-payment；第二次请求应安全返回重复结果，不产生额外支付/保单。是否允许客户端省略幂等键需产品确认。
- 状态：当前行为可验证 / 需求确认。

### FT-PAY-009 — 幂等键为空字符串或纯空白

- 优先级：P1
- 类型：边界 / 幂等
- 前置条件：Approved 申请。
- 数据：idempotencyKey="" 和仅空格。
- 步骤：分别测试空字符串与空白键，且每个场景使用独立申请。
- 预期结果：当前实现与缺失键相同，使用默认键；重试安全。需确认 API 是否应改为拒绝空键。
- 状态：当前行为可验证 / 需求确认。

- 前置条件：Approved 申请。
- 数据：第一次使用 "  key-123  "，第二次使用 "key-123"。

- 预期结果：当前实现 Trim 后视为同一键；第二次 duplicate=true；paymentId 和 policyNumber 相同；没有重复数据。
- 状态：现状可验证。

### FT-PAY-011 — 幂等键长度超过数据库限制

- 优先级：P1
- 类型：负向 / 数据库边界
- 前置条件：Approved 申请和专用测试数据库。
- 数据：Trim 后长度 101 的幂等键。
- 步骤：调用支付接口，检查状态码、错误体和数据副作用。
- 预期结果：合理目标为明确 4xx 且不创建支付/保单；不得出现未处理 500 或半完成状态。当前代码未显式校验 100 字符上限，重点验证并记录风险。
- 状态：实现风险 / 需求确认。

### FT-PAY-012 — 支付成功后申请状态与金额一致

- 优先级：P0
- 类型：数据一致性
- 前置条件：Approved 申请，记录 premium。
- 数据：唯一幂等键。
- 步骤：支付成功后查询申请及关联保单/支付数据；若只能通过 API 查询部分字段，则在集成测试中补数据库断言。
- 预期结果：申请为 Paid；支付金额等于申请 premium；支付状态 Succeeded；保单 Active；关联 applicationId 一致。
- 状态：部分可由当前公开 API 验证，支付表金额需集成测试验证。

### FT-PAY-013 — 支付失败路径无副作用

- 优先级：P0
- 类型：负向 / 事务一致性
- 前置条件：Pending 或 Rejected 申请。
- 数据：唯一幂等键。
- 步骤：调用支付接口并检查申请状态、支付和保单。
- 预期结果：返回 409；申请状态不变；无支付和保单记录。
- 状态：现状可验证。数据库级无记录断言属于集成测试。

### FT-PAY-014 — 负数、零或极大申请 ID

- 优先级：P1

- 前置条件：API 可用。

- 预期结果：不返回 500；不存在的资源按约定返回 404 或明确 4xx；不得创建数据。

### FT-PAY-015 — 并发相同键重复支付

- 优先级：P0
- 类型：并发 / 集成测试
- 前置条件：专用测试库中有一条 Approved 申请。
- 数据：多个并发请求使用同一个幂等键。
- 步骤：并发发送 5 个相同支付请求；随后检查最终申请、支付和保单数据。
- 预期结果：最终最多一笔支付和一张保单；所有成功响应应指向同一结果，冲突响应应符合契约；不得出现未处理 500 或半完成状态。
- 状态：实现风险，需要在专用环境验证。

### FT-PAY-016 — 并发不同键支付同一申请

- 优先级：P0
- 类型：并发 / 业务唯一性
- 前置条件：专用测试库中有一条 Approved 申请。
- 数据：并发请求分别使用 K1、K2。
- 步骤：并发发起支付，随后检查最终数据。
- 预期结果：最多一笔有效支付和一张保单；申请最终为 Paid；任何失败请求不得造成重复数据或半完成状态。
- 状态：实现风险；需验证事务与唯一约束竞争。

### FT-PAY-017 — 支付请求超时后的安全重试

- 优先级：P1
- 类型：可靠性 / 幂等
- 前置条件：隔离测试环境可模拟响应丢失但服务端可能已提交。
- 数据：Approved 申请、固定幂等键 K。
- 步骤：首次请求在客户端超时或丢弃响应后，使用同一个 K 重试。
- 预期结果：最终只有一笔支付和一张保单；重试返回既有结果或明确可恢复错误；不得使用新键盲目重试。
- 状态：可靠性测试；需要可控网络故障工具。

- 优先级：P0

- 数据：同一申请 ID。
- 步骤：使用新幂等键再次请求支付。
- 预期结果：当前实现先检查已存在幂等键，再检查状态；新键请求应返回 409，且不新增支付/保单。
- 状态：现状可验证。
