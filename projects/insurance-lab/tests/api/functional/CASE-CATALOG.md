# API 功能测试用例总索引

## 目的与使用规则

本索引只负责导航。每个接口的可执行测试设计放在独立文件中，避免把不同接口、不同前置条件和不同断言混在一个大表里。

每条用例均应具备：ID、标题、优先级、测试类型、前置条件、数据、步骤、预期结果、实现状态/风险。执行结果另记录为 Pass / Fail / Blocked / Not Run，并关联缺陷编号。

## 测试基线和风险标记

- 【现状可验证】：根据当前 Program.cs 可以直接验证当前行为；不等于该行为已获产品需求批准。
- 【需求确认】：需要产品/接口契约明确后才能判定通过或失败。
- 【实现风险】：当前代码存在未显式校验、异常路径或安全能力缺口，需要重点验证并按实际结果提缺陷。
- 【安全阻断】：若系统用于真实业务，必须由产品/安全负责人确认风险接受情况；不能仅因当前没有认证接口就把未授权访问视为符合要求。
- 当前接口基线来源为后端 Minimal API Handler；如仓库中的 Swagger/OpenAPI、需求文档或验收标准与代码不一致，应登记差异，不得自动以代码覆盖需求。

## 优先级定义

- P0：核心业务正确性、资金/保单一致性、状态机、安全上线阻断。
- P1：主要校验、接口契约、常见异常与数据一致性。
- P2：健壮性、排序、兼容性、极端输入和补充回归。

## 执行注意事项

1. 所有写操作使用本次测试创建的申请 ID 和唯一幂等键。
2. 验证拒绝请求时，不能只断言 HTTP 状态码；还要验证申请状态、支付记录和保单没有不应发生的变化。
3. 并发、数据库约束和事务回滚属于集成测试重点；需要专用测试数据库和可控故障注入，不要在共享/生产数据库操作。
4. 当前现有 pytest 文件仍保留作为基础回归入口；本目录的 Case 文档是测试设计资产，不代表所有 Case 已自动化或已执行。
