# GET /health — API 测试用例

## 接口契约基线

- 方法/路径：GET /health
- 当前实现成功响应：HTTP 200，JSON 包含 status=ok、service=insurance-api。
- 认证：当前代码未配置认证。
- 用例状态说明：按当前代码验证响应；健康检查是否还需检查数据库连接，属于需求确认项。

## 用例

### FT-HEALTH-001 — 健康检查返回成功

- 优先级：P0
- 类型：功能 / 冒烟 / 自动化候选
- 前置条件：API 服务已启动，测试环境地址可访问。
- 测试数据：无。
- 步骤：
  1. 向 /health 发送 GET 请求。
  2. 检查 HTTP 状态码、Content-Type 和响应 JSON。
- 预期结果：
  1. HTTP 状态码为 200。
  2. 响应体可解析为 JSON 对象。
  3. status 精确等于 ok。
  4. service 精确等于 insurance-api。
  5. 不包含堆栈、连接串、密钥等内部敏感信息。
- 状态：现状可验证。

### FT-HEALTH-002 — 健康检查重复调用稳定

- 优先级：P1
- 类型：健壮性 / 自动化候选
- 前置条件：API 服务正常运行。
- 测试数据：连续请求 10 次。
- 步骤：
  1. 连续发送 10 次 GET /health。
  2. 逐次记录状态码和响应体。
- 预期结果：
  1. 所有请求均返回 200 和相同的健康字段。
  2. 不因重复调用产生业务数据。
  3. 不出现 5xx。
- 状态：现状可验证。

### FT-HEALTH-003 — 健康接口是否反映数据库不可用

- 优先级：P2
- 类型：可靠性 / 需求确认
- 前置条件：隔离测试环境；能够安全地模拟数据库不可用。
- 测试数据：数据库连接不可用。
- 步骤：
  1. 在隔离环境中停止/阻断测试数据库连接。
  2. 请求 GET /health。
  3. 恢复数据库并确认服务恢复。
- 预期结果：由健康检查需求定义。如果 /health 仅表示进程存活，则可仍返回 200；如果它承诺依赖就绪，则应返回非健康结果。不得在未确认契约前直接判定。
- 状态：需求确认；当前 handler 不访问数据库，因此不检查数据库就绪。
- 风险说明：不得在共享或生产环境执行故障注入。
