# 保险业务跨接口工作流测试用例

## 目的

本文件验证多个接口组合后的业务不变量。单接口测试通过不代表完整业务流正确。写操作均使用本次创建的 applicationId；需要支付表精确断言的场景应在 integration 测试中补充数据库验证。

## 用例

### FT-FLOW-001 — 创建、核保通过、支付、查询保单完整成功流

- 优先级：P0
- 类型：端到端功能 / 冒烟
- 前置条件：API 和专用测试数据库可用。
- 数据：唯一申请人、age=30、productCode=LIFE-BASIC、premium=1250.00、唯一幂等键。
- 步骤：
  1. POST /api/applications 创建申请。
  2. 断言 201 并记录 applicationId。
  3. POST /api/applications/{id}/underwrite，approve=true。
  4. 断言 200 和 Approved。
  5. POST /api/applications/{id}/pay，使用唯一幂等键。
  6. 断言 200、Succeeded、Active、duplicate=false。
  7. GET /api/applications，检查该申请状态。
  8. GET /api/policies，检查该申请的保单。
  9. GET /api/policies/{policyId}，核对详情。
- 预期结果：状态依次为 Pending→Approved→Paid；恰好一张 Active 保单；申请人、保费和申请 ID 关联正确；所有接口返回符合各自契约。
- 状态：现状可验证。

### FT-FLOW-002 — 核保拒绝后禁止支付

- 优先级：P0
- 类型：端到端负向
- 前置条件：API 可用。
- 数据：合法申请和唯一幂等键。
- 步骤：创建申请→核保 approve=false→尝试支付→查询申请及保单。
- 预期结果：创建 201；核保 200/Rejected；支付 409；申请保持 Rejected；无支付/保单。
- 状态：现状可验证。

### FT-FLOW-003 — Pending 申请不允许跳过核保直接支付

- 优先级：P0
- 类型：端到端负向 / 状态机
- 前置条件：新建申请，未核保。
- 数据：唯一幂等键。
- 步骤：创建申请后直接支付；查询申请和保单。
- 预期结果：支付 409；申请保持 Pending；无支付/保单。
- 状态：现状可验证。

### FT-FLOW-004 — 重复支付不会重复签发

- 优先级：P0
- 类型：端到端幂等
- 前置条件：申请已核保通过。
- 数据：固定幂等键 K。
- 步骤：完成首次支付；使用 K 重试两次；查询保单列表。
- 预期结果：首次 duplicate=false，后续请求 duplicate=true；paymentId 和 policyNumber 不变；该申请仅有一张保单。
- 状态：现状可验证。

### FT-FLOW-005 — 跨申请复用幂等键被拒绝且不污染数据

- 优先级：P0
- 类型：端到端隔离
- 前置条件：申请 A、B 均已核保通过；A 已使用 K 支付成功。
- 数据：申请 B 使用 K。
- 步骤：尝试支付 B；查询 A、B 的申请和保单。
- 预期结果：B 返回 409；A 仍 Paid 且保单不变；B 保持 Approved 且无支付/保单；响应不泄露 A 的支付/保单信息。
- 状态：现状可验证。

### FT-FLOW-006 — 同一申请不同幂等键重试

- 优先级：P0
- 类型：端到端幂等 / 业务唯一性
- 前置条件：申请已核保通过并成功支付一次。
- 数据：首次 K1，重试 K2。
- 步骤：使用 K2 再次支付，查询申请和保单。
- 预期结果：当前实现返回 409；申请保持 Paid；仍只有一张保单且无第二笔支付。最终响应语义应由业务契约确认。
- 状态：现状可验证 / 需求确认。

### FT-FLOW-007 — 创建申请校验失败不会污染后续流程

- 优先级：P1
- 类型：端到端负向 / 数据完整性
- 前置条件：API 可用。
- 数据：age=17，其他字段有效且申请人使用唯一标识。
- 步骤：提交非法创建请求；查询申请列表；确认没有该申请；再使用合法数据创建一条新申请并完成主流程。
- 预期结果：非法请求 400 且无记录；后续合法流程正常完成；前一个失败请求不影响后一个申请。
- 状态：现状可验证。

### FT-FLOW-008 — 多个申请之间的数据隔离

- 优先级：P0
- 类型：数据隔离
- 前置条件：创建申请 A、B，使用不同申请人、保费和幂等键。
- 数据：A premium=100.00，B premium=200.00。
- 步骤：分别核保并支付；查询申请列表、保单列表和两张保单详情。
- 预期结果：每张保单只关联自己的 applicationId；申请人和保费不串单；A 的幂等键不能让 B 返回 A 的支付结果。
- 状态：现状可验证。

### FT-FLOW-009 — API 错误响应不暴露内部敏感信息

- 优先级：P1
- 类型：安全 / 错误处理
- 前置条件：API 可用。
- 数据：不存在的申请 ID、重复核保、非法年龄。
- 步骤：分别触发 404、409、400；检查响应正文。
- 预期结果：错误体可解析且包含适当业务信息；不包含堆栈、SQL、数据库地址、连接串或密钥。
- 状态：现状待验证。

### FT-FLOW-010 — 未授权访问风险登记

- 优先级：P0（生产上线阻断评估）
- 类型：安全 / 授权
- 前置条件：明确当前系统是否应仅限登录用户使用；在隔离测试环境进行。
- 数据：未登录请求；若系统定义用户身份，再准备用户 A、B。
- 步骤：
  1. 未携带身份凭据调用申请列表、保单列表和支付接口。
  2. 若存在用户身份机制，再用用户 A 的身份读取用户 B 的资源。
- 预期结果：以安全需求为准；若这些是受保护的真实业务数据，未授权请求应被拒绝，跨用户资源访问应返回 403/404。当前代码未配置认证/对象级授权，因此当前行为应登记为安全缺口，而非直接判定业务验收通过。
- 状态：安全阻断 / 需求确认。
