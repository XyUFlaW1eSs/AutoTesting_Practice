# POST /api/applications/{id}/underwrite — API 测试用例

## 接口契约基线

请求体包含 approve（布尔值）和 note。仅 Pending 申请允许核保；approve=true 转为 Approved，false 转为 Rejected；已不存在的申请返回 404，非 Pending 状态返回 409。当前 note 仅在响应中回显，没有持久化。

## 用例

### FT-UW-001 — Pending 申请核保通过

- 优先级：P0
- 类型：功能 / 主流程
- 前置条件：已通过 POST /api/applications 创建一条申请，状态为 Pending。
- 数据：approve=true，note="QA approval"。
- 步骤：
  1. POST /api/applications/{id}/underwrite。
  2. 检查响应。
  3. GET /api/applications，按 id 查询状态。
- 预期结果：HTTP 200；响应 id 正确、status=Approved、note 与请求一致；列表状态更新为 Approved；没有支付或保单记录被创建。
- 状态：现状可验证。

### FT-UW-002 — Pending 申请核保拒绝

- 优先级：P0
- 类型：功能 / 主流程
- 前置条件：已创建 Pending 申请。
- 数据：approve=false，note="QA rejection"。
- 步骤：调用核保接口并查询申请列表。
- 预期结果：HTTP 200；响应 status=Rejected；申请列表状态为 Rejected；没有支付或保单产生。
- 状态：现状可验证。

### FT-UW-003 — 已 Approved 申请再次核保

- 优先级：P0
- 类型：状态机 / 负向
- 前置条件：申请已核保通过。
- 数据：再次提交 approve=false。
- 步骤：调用核保接口，随后查询申请状态。
- 预期结果：HTTP 409；错误信息说明当前状态不允许核保；状态仍为 Approved，不得被改成 Rejected。
- 状态：现状可验证。

### FT-UW-004 — 已 Rejected 申请再次核保

- 优先级：P0
- 类型：状态机 / 负向
- 前置条件：申请已核保拒绝。
- 数据：再次提交 approve=true。
- 步骤：调用核保接口，随后查询申请状态。
- 预期结果：HTTP 409；状态仍为 Rejected，不得被改成 Approved。
- 状态：现状可验证。

### FT-UW-005 — 已 Paid 申请再次核保

- 优先级：P0
- 类型：状态机 / 负向
- 前置条件：申请已完成支付并变为 Paid。
- 数据：approve=false。
- 步骤：调用核保接口，再查询申请和保单。
- 预期结果：HTTP 409；申请仍为 Paid；已签发保单不变。
- 状态：现状可验证。

### FT-UW-006 — 不存在的申请 ID

- 优先级：P1
- 类型：负向 / 资源不存在
- 前置条件：确认该 ID 在测试库不存在。
- 数据：不存在的正整数 ID。
- 步骤：调用核保接口。
- 预期结果：HTTP 404；返回可解析错误 JSON；不泄露 SQL、连接串或堆栈；无数据变化。
- 状态：现状可验证。

### FT-UW-007 — ID 为零或负数

- 优先级：P1
- 类型：边界 / 路由约束
- 前置条件：API 可用。
- 数据：id=0、id=-1。
- 步骤：分别调用核保接口。
- 预期结果：不返回 500；按路由约束通常为 404，最终以接口契约确定；不修改任何申请。
- 状态：现状待运行验证。

### FT-UW-008 — approve 字段缺失、null 或类型错误

- 优先级：P1
- 类型：负向 / 模型绑定
- 前置条件：存在 Pending 申请。
- 数据：分别省略 approve、approve=null、approve="yes"。
- 步骤：逐组调用核保接口。
- 预期结果：请求应返回 4xx，不应把无效值默认为通过或拒绝；申请仍为 Pending。
- 状态：当前 request 模型及绑定行为需结合 DTO 定义和实际运行确认。

### FT-UW-009 — note 缺失、null、空串和中文

- 优先级：P2
- 类型：健壮性 / 契约
- 前置条件：存在 Pending 申请。
- 数据：分别省略 note、null、空串、中文文本。
- 步骤：逐组核保；每组使用独立申请。
- 预期结果：note 是否必填、是否允许 null 需由契约定义；无论如何，核保结果只能由 approve 决定。当前实现把 note 原样回显且不持久化。
- 状态：需求确认。

### FT-UW-010 — note 超长输入

- 优先级：P2
- 类型：边界 / 健壮性
- 前置条件：存在 Pending 申请。
- 数据：非常长的 note（例如 10,000 字符）。
- 步骤：提交核保请求。
- 预期结果：按契约拒绝或安全处理；不得返回未处理 500；不能改变 approve 的业务含义。最大长度需产品/接口规范明确。
- 状态：需求确认 / 待运行验证。

### FT-UW-011 — 核保失败不改变状态

- 优先级：P0
- 类型：数据一致性
- 前置条件：已有 Approved 申请。
- 数据：重复核保请求。
- 步骤：
  1. 记录当前状态。
  2. 再次调用核保接口。
  3. 查询申请列表。
- 预期结果：接口返回 409；状态和更新时间不发生不应有的变化；不创建支付或保单。
- 状态：现状可验证；更新时间精确断言需考虑时间精度。

### FT-UW-012 — 并发核保竞争

- 优先级：P1
- 类型：并发 / 集成测试候选
- 前置条件：专用测试库中有一条 Pending 申请。
- 数据：两个并发请求分别 approve=true 和 approve=false。
- 步骤：近同时发送两个核保请求，随后查询申请状态。
- 预期结果：最终状态只能是 Approved 或 Rejected 之一，不应出现非法状态；应有明确的冲突语义。当前实现没有显式并发令牌，可能存在竞态，需实际验证并评估是否修复。
- 状态：实现风险；使用专用测试环境。
