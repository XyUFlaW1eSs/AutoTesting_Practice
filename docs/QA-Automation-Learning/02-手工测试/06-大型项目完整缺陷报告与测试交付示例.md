# 大型项目完整缺陷报告与测试交付示例

本案例模拟虚构保险平台一次迭代验收。编号、账号、保单号、金额均为学习用数据，不代表真实系统。报告可迁移到 Jira、禅道、Azure DevOps 等工具。

## 1. 项目背景

| 项目项 | 示例内容 |
|---|---|
| 项目 | 星海保险在线服务平台（虚构） |
| 版本 | Web 2.8.0-rc.3 / API v1 |
| 环境 | QA，Chrome 稳定版，Windows 11，隔离测试数据库 |
| 周期 | 2026-10-12 至 2026-10-16 |
| 范围 | 投保申请、核保、模拟支付、保单生成、保单查询、角色权限 |
| 排除项 | 真实支付渠道、真实客户数据、生产压测 |
| 核心目标 | 合法申请可提交；核保通过才可支付；支付成功最多生成一份有效保单；支付失败不得生成有效保单；查询必须授权；UI/API/DB 状态一致 |

## 2. 缺陷分级与状态流转

### 严重程度 Severity
- S1 致命/阻断：核心业务不可用、重大数据损坏、严重安全/越权风险，无可接受绕过方案。
- S2 严重：关键业务路径错误、错误生成/遗漏保单或金额，影响范围较大。
- S3 一般：非核心功能异常，有可行绕过方案或局部不符合需求。
- S4 轻微：文案、布局或低影响视觉问题。

### 优先级 Priority
- P0 立即处理，阻断发布或存在重大风险。
- P1 本迭代必须修复，影响关键路径或验收项。
- P2 计划修复，影响有限且有绕过方式。
- P3 可排期优化。

严重程度衡量影响大小；优先级衡量处理紧迫度。两者不能机械一一对应。

### 状态流转
新建 → 待确认/已确认 → 已分配 → 修复中 → 待验证 → 关闭。
复测失败时重新打开，并附上新版本、复现步骤和新证据。重复缺陷、需求变更或非缺陷也要记录判定依据，不能直接删除。

## 3. 完整缺陷 A：重复支付生成重复保单

### 基本信息
| 字段 | 内容 |
|---|---|
| ID | INS-2841 |
| 标题 | [支付/保单][S2][P1] 同一投保单重复提交支付请求后生成两份有效保单 |
| 模块 | 投保 → 支付 → 保单生成 |
| 发现版本 | Web 2.8.0-rc.3 / API v1 |
| 环境 | QA，隔离测试数据库 |
| 严重程度/优先级 | S2 / P1 |
| 发现日期 | 2026-10-14（示例） |
| 指派对象 | 支付服务负责人（示例角色） |
| 状态 | 待验证（示例） |
| 标签 | regression, idempotency, policy-creation |

### 前置条件
- 测试用户已登录。
- 虚构申请 APP-TEST-10081 已核保通过。
- 该申请尚未支付、未生成保单。
- 使用模拟支付，金额 1200.00。
- 两次请求使用同一业务幂等键 PAY-TEST-10081。

### 复现步骤
1. 提交支付请求，申请号 APP-TEST-10081，幂等键 PAY-TEST-10081。
2. 保存第一次响应中的状态、支付单号、保单号、请求关联 ID。
3. 第一次请求完成后，使用相同业务参数和幂等键再次提交。
4. 查询支付记录和保单记录，按申请号核对关联数据。
5. 保存两次请求/响应和只读查询结果。

### 预期结果
- 第二次请求返回第一次操作的可识别结果，或按 API 合同返回明确的重复请求响应。
- 同一申请最多存在一笔成功的业务支付结果和一份有效保单。
- 不产生重复扣款或重复保单；服务端具备唯一约束、事务保护或等效并发保护。

### 实际结果（模拟观察）
- 第一次请求成功，生成 POL-TEST-51001。
- 第二次请求也返回成功，生成 POL-TEST-51002。
- 同一申请关联两份有效保单。
- 这是用于练习如何写报告的模拟结果，不代表任何真实系统。

### 证据清单
- INS-2841-01-request-1.json：第一次请求。
- INS-2841-02-response-1.json：第一次响应。
- INS-2841-03-request-2.json：重复请求。
- INS-2841-04-response-2.json：第二次响应。
- INS-2841-05-db-check.sql：只读核对 SQL。
- INS-2841-06-db-result.csv：虚构查询结果。
- INS-2841-07-timeline.md：请求时间、关联 ID 和操作顺序。
- 证据必须遮蔽真实 Token、Cookie、账号及个人信息。

### 影响分析
业务上可能产生重复有效保单，导致账务、理赔、客服数据不一致。即使前端按钮禁用，网络重试、客户端超时重放和并发请求仍可能触发。修复并通过顺序重复、并发重复和超时后重放测试前，不建议通过该验收项。

### 修复沟通建议
- 服务端实施业务幂等保护，不只依赖前端防抖。
- 为申请与成功支付、申请与有效保单设计唯一约束或等效事务保护。
- 明确重复请求的响应契约与关联 ID。
- 增加并发提交回归测试。

## 4. 完整缺陷 B：支付失败后仍生成有效保单

### 基本信息
| 字段 | 内容 |
|---|---|
| ID | INS-2848 |
| 标题 | [支付/保单][S2][P1] 模拟支付失败后保单仍被创建为有效状态 |
| 模块 | 支付结果处理、保单状态机 |
| 版本/环境 | Web 2.8.0-rc.3 / API v1，QA |
| 严重程度/优先级 | S2 / P1 |
| 状态 | 已确认（示例） |

### 前置条件与步骤
1. 建立已核保通过、尚未支付的虚构申请。
2. 在模拟支付渠道设置为支付失败。
3. 提交支付请求，保存响应和业务关联 ID。
4. 查询申请、支付和保单状态，并刷新保单查询页面。

### 预期结果
支付记录应为失败或按合同约定的待处理状态，不得生成有效保单。若创建临时草稿，必须明确标识为非有效状态。

### 实际结果（模拟）
支付结果为失败，但查询页面和数据库均显示保单有效。

### 影响与证据
违反“支付成功后才能生效”的业务约束，可能造成保费与保障状态不一致。附请求/响应、模拟网关结果、申请/支付/保单状态快照和时间线。修复后验证成功、失败、超时未知、重复回调、乱序回调及重试。

## 5. 完整缺陷 C：越权查询其他用户的保单

### 基本信息
| 字段 | 内容 |
|---|---|
| ID | INS-2852 |
| 标题 | [权限/保单查询][S1][P0] 普通用户可通过修改保单号查询其他用户的保单 |
| 模块 | 身份认证、对象级授权、保单查询 API |
| 环境 | 仅授权 QA 环境与虚构测试账号 |
| 严重程度/优先级 | S1 / P0 |
| 状态 | 已确认（示例） |

### 安全边界
仅使用批准的 QA 环境、自己创建的虚构账号和虚构保单。不得枚举真实保单号或访问真实客户信息。

### 复现步骤
1. 使用测试用户 A 创建一份虚构保单。
2. 使用测试用户 B 登录并取得其自己的会话。
3. 确认用户 B 可查询自己的保单。
4. 在 QA 环境把查询请求的保单号改为用户 A 的虚构保单号。
5. 记录状态码、响应是否包含数据及授权日志。

### 预期结果
服务端校验当前用户对目标保单的访问权限；未授权时拒绝请求且不泄露详情。

### 实际结果（模拟）
接口返回用户 A 的虚构保单详情。

### 影响与处理
此类问题应立即升级安全负责人。不能只在前端隐藏按钮，必须服务端执行对象级授权。修复后覆盖本人保单、他人保单、未登录、管理员角色、列表与导出等入口。证据应最小化并避免包含真实敏感数据。

## 8. 测试总结报告示例

| 指标 | 示例值 |
|---|---:|
| 计划用例 | 120 |
| 已执行 | 105 |
| 通过 | 92 |
| 失败 | 8 |
| 阻塞 | 5 |
| 未执行 | 15 |
| 执行率 | 87.5%（105/120） |
| 已执行用例通过率 | 87.6%（92/105） |

执行率 = 已执行 / 计划；已执行用例通过率 = 通过 / 已执行。必须说明统计口径，不能把阻塞或未执行算作通过。

**结论摘要：** 当前版本仍有未关闭的高风险缺陷，不能仅凭用例通过率判断可发布。建议暂缓相关验收，待安全授权、支付/保单一致性缺陷修复并回归通过后重新评估。

**未解决风险：** 支付幂等性、失败状态转换、对象级授权及未执行用例。每项应记录影响、补测计划和责任人。

**验收建议：** S1/P0 安全或数据完整性问题未解决时，不应以总体通过率掩盖风险。最终发布决定由授权业务/产品/技术负责人作出；若接受风险，应记录具体缺陷、影响、补偿措施、责任人与批准记录。
