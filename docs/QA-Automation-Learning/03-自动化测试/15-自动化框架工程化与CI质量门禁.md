# 自动化框架工程化与 CI 质量门禁

参考：[pytest](https://docs.pytest.org/en/stable/contents.html)、[GitHub Actions](https://docs.github.com/en/actions)、[Playwright Python](https://playwright.dev/python/docs/intro)。

## 课 1：先决定测试层级
- 单元测试：快速、隔离、验证纯规则。
- API/集成测试：验证服务边界、业务流程和数据副作用。
- UI 测试：验证关键用户旅程、可见行为和浏览器集成。
- 手工探索：验证模糊需求、易用性和未预设风险。
不要为了自动化数量，把同一规则只在慢速 UI 层重复验证。

## 课 2：推荐项目结构
    src/
      rules/
      clients/
      data/
    tests/
      unit/
      api/
      integration/
      ui/
      conftest.py
    test-data/
    artifacts/
    pytest.ini
职责：rules 放纯业务规则；clients 封装 HTTP；data 放可验证的数据构造；tests 只保留测试场景与断言；artifacts 保存报告与失败证据。

## 课 3：配置与秘密管理
环境配置包括 base URL、超时、浏览器、日志级别等。可将非秘密配置放环境变量或配置文件；Token、密码、私钥必须使用安全的环境/Secrets，不提交仓库，不打印完整值。对不同环境做显式校验，避免误打生产地址。

## 课 4：API client 与错误处理
统一管理 Session、默认头、timeout 和错误分类；不要把所有 HTTP 错误都转换为成功返回值。日志要记录业务关联 ID、路径、耗时和状态，敏感字段脱敏。重试需明确哪些操作可安全重试。

## 课 5：数据工厂与隔离
每次运行生成唯一的虚构申请 ID；准备数据与清理逻辑分开；失败时保留足够证据；并行执行时避免共用可变记录。测试清理不得影响其他测试数据。

## 课 6：日志、报告和证据
至少保存 pytest 结果、JUnit XML、失败日志和 UI 截图/trace。报告应有测试用例 ID、环境、版本、失败原因与关联业务 ID。避免在报告中保存秘密凭据和真实个人信息。

## 课 7：Flaky 测试治理
将失败分类为产品缺陷、测试代码问题、环境问题、数据问题或时序问题。追踪失败率与重试后通过率。修复根因而非单纯提高超时；重试不能掩盖发布风险。

## 课 8：Git 分支与 Pull Request
建议每个学习任务使用短分支，提交信息表达变更目的；提交前运行格式检查和测试；PR 描述包括范围、风险、测试命令、结果和截图。Review 检查断言质量、数据清理、秘密信息和测试层级。

## 课 9：GitHub Actions 最小工作流
    name: QA learning tests
    on:
      push:
        paths:
          - 'tests/**'
          - 'src/**'
          - '.github/workflows/**'
      pull_request:
        paths:
          - 'tests/**'
          - 'src/**'
          - '.github/workflows/**'
      workflow_dispatch:
    jobs:
      test:
        runs-on: ubuntu-latest
        steps:
          - uses: actions/checkout@v4
          - uses: actions/setup-python@v5
            with:
              python-version: '3.12'
          - run: python -m pip install -r requirements.txt
          - run: python -m pytest -q --junitxml=artifacts/junit.xml
此为教学示例，实际仓库要确保依赖文件存在、输出目录提前创建，并按组织的 Action 版本和安全策略维护。

## 课 10：CI 制品与失败诊断
工作流应上传 JUnit XML 和必要的失败截图/trace。CI 失败时先查看 job step、测试摘要、失败断言、日志和产物；区分测试失败与安装/环境失败。不要只看绿色徽标。

## 课 11：质量门禁策略
PR 快速检查：格式/静态检查、单元测试、少量 API 冒烟；合并后或夜间：更完整的 API/集成/浏览器矩阵。门禁应基于风险、执行时间和可靠性设定。高风险失败不能因重跑通过而自动视为无风险。

## 课 12：交付可复现性
README 必须说明 Python 版本、环境准备、安装命令、测试命令、环境变量、数据准备、报告路径、清理方式和常见错误。新机器按 README 操作应能复现结果。

## 结业任务
把保险业务规则测试接入 CI；在 PR 中自动运行，失败时工作流应失败，成功/失败都能查看报告。故意制造一条失败用例，确认 CI 能拦截；再恢复用例并验证报告可读。
